Local-first video search

Search hours of footage by describing what you are looking for.

Type “someone carrying a bag near the door” and get the moment, not the file. Everything runs on the machine the video is already on — no upload, no account, no cloud bill. A phone on the same WiFi can add clips to it in seconds.

The idea

Index the footage. Don’t summarise it.

The obvious way to make video searchable is to caption every frame with a large model. It is also unaffordable: an hour of video is ninety thousand frames, and a caption model that takes a second each turns one hour of footage into a day of compute.

So nothing here describes video. It indexes it — building a small set of structured facts per moment (what moved, what was detected, who it was, what was said) and searching those. The expensive models only ever see the fraction of frames that survived everything cheaper.

That inversion is the whole architecture. Each stage is allowed to be expensive only because the stage before it threw most of the work away.

Motion triage

Two tiers. The first reads compressed packet sizes without decoding anything — a static camera produces small packets, so most of a night is rejected at the cost of reading the file. Only what survives gets decoded for background subtraction.

PyAV packet sizes · OpenCV MOG2

Detection and tracking

Objects per frame, then linked across frames into tracklets, so a person crossing a room is one thing that moved rather than forty unrelated boxes.

YOLO11n ONNX · ByteTrack association · YOLOX-tiny where the licence matters

02

Zones and identity

Regions drawn on the video turn positions into events — entered, left, crossed a line, and which side of it. Faces are matched against people you have named once.

SCRFD + ArcFace · YuNet + SFace as the shippable pair · point-in-polygon events

03

Semantic embedding

Each surviving moment gets a CLIP vector, which is what lets a description match something nobody labelled — the difference between searching for person and searching for someone waiting by a door.

CLIP image + text encoders, exported to ONNX separately

04

Captions

A vision-language model describes what a tracked person is actually doing. This is the only stage that produces the word “bag” or “medicine” — no detector has those categories.

Florence-2-base ONNX, encoder–decoder with KV cache

05

Speech

Voice activity detection gates the audio, so silence costs almost nothing. Output is filtered on the model’s own confidence — the failure mode of a transcript is not a gap, it is a fluent sentence nobody said.

Whisper base via CTranslate2 · int8 · ~15× realtime on CPU

Answering a query

Two searches, fused

Everything the stages produced — object labels, names, zone events, captions and speech — is flattened into one text document per moment and indexed with SQLite’s FTS5. A query then runs twice: semantically against the CLIP vectors, and lexically against that text.

The two rankings are combined with reciprocal rank fusion, which needs no score calibration between two systems that do not share units. It matters more than it sounds: a search for a spoken name returned the right moment ranked first even though four other moments scored higher on visual similarity. The lexical hit carried it.

Why speech earns its place

It is the only stage that can produce a name nobody enrolled, or a word for something off camera — a knock, a doorbell, someone called from another room.

The phone path

A QR code, a six-digit code, and no app to install

The same FastAPI server that backs the desktop window can be exposed to the local network. A phone scans a QR code, types a six-digit pairing code, and gets a signed cookie naming a row in a devices table — so revoking access is a delete, not a secret rotation.

Uploads are resumable by construction: the offset a client is told to resume from is os.stat on the partial file, never a counter that could drift from what is actually on disk. A dropped lift, a locked screen, a walk out of WiFi range — the transfer picks up where the bytes end.

Until a device pairs it can reach exactly four paths. The allow-list is a closed set rather than a /static/ prefix, because the obvious version of that rule hands your entire application to a device that has proved nothing.

Decisions

Three that shaped everything else

Licensing as an engineering constraint
The best detector available, YOLO11, is AGPL-3.0; the best face stack, InsightFace, is research-only. Both are still the default, and neither can ship. So a permissive alternative was built for each — YOLOX (Apache-2.0) and YuNet + SFace (MIT / Apache-2.0) — selectable rather than swapped in, because face-similarity thresholds differ between stacks and changing one silently would invalidate every identity already enrolled. YOLOX meant writing a decoder by hand: different tensor layout, colour order and padding, each of which fails silently.
A runtime that stays small
PyTorch is two gigabytes. It appears here only inside a throwaway .venv-export used to convert models, and never at inference. What actually runs is ONNX Runtime, NumPy and CTranslate2.
Backends chosen by measurement
The runtime is selected at load time and the winner is reported, not assumed. On the baseline laptop the surprise was that Intel’s own CPU path lost to ONNX Runtime’s — so it sits last, despite the badge.

A bug this found

With seven phones, the first search took 10.7 seconds. The text encoder was built lazily with no lock, so all seven arrivals found it missing and all seven started building it. A mutex and a warm-up thread took the worst request to 611 ms.

Other measurements that overturned the plan: reusing CLIP as a body-identity signal (same person 0.818, person vs. bird 0.805 — indistinguishable, so it was cut), and the larger caption model, which lost the words bag, carrying and bed and was rolled back.
